# Codex Prompt — Bring the Boss Clinician admin to Kajabi feature parity

Paste everything below into Codex as a single task brief. It is written to be executed
incrementally: **Phase 0 (bugs) must ship before Phase 1**, because several "missing
features" are actually working features whose data is not wired up.

Scope note: **website builder / page builder / landing-page design and the mobile app are
explicitly out of scope.** Do not build a drag-and-drop site builder, theme editor, custom
code editor, branded mobile app, or blog/testimonial/resource page design work. Everything
else in Kajabi is in scope.

---

## CONTEXT

You are working on `bossclinician.callsphere.site` — a React/Vite + Node admin
("Admin Studio") that is a self-hosted Kajabi replacement. Admin routes live under
`/admin/*`; public routes include `/f/:slug` (forms), `/quiz/:slug`, `/events/:slug`,
`/checkout/:slug`. Payments run through Stripe. The stack already has:

Products (courses, community, media library, coaching, podcasts, newsletters, downloads),
Sales (offers with price/order-form/bumps/upsells/after-purchase, payments, plans,
subscriptions, invoices, coupons, payouts→Stripe, partners/affiliates), Marketing
(campaigns, funnels, sequences, automations v2, system emails, quizzes, events, forms),
Contacts (people, groups/segments, tags, enquiries, AI conversations, members,
subscribers), Analytics (overview + ~40 reports), Settings (general, payments/checkout,
email, customers, course delivery, coaching, marketing, website, integrations, team,
connections).

It is already close to Kajabi at the navigation level. The real gaps are (a) broken wiring
between modules, and (b) depth inside a handful of modules.

## PHASE 0 — BUGS FOUND BY LIVE TESTING (fix these first, highest priority)

Each item below was reproduced by hand in the live admin. Fix the cause, not the symptom,
and add a regression test for each.

### P0-0. Automations never run on real events — the engine is decorative  ⭐⭐ WORST BUG
**Reproduce (done end to end):** create an automation with trigger
`a tag is added to someone → Retreat Waitlist 2027` and one step
`start them on an email sequence → ZZ Test — welcome sequence`. Confirm the list shows it as
**RUNNING** with no "needs attention" warning. Un-pause the target sequence
("Start sending"). Then open a contact and apply the **Retreat Waitlist 2027** tag.
**Observed:** the tag is applied to the contact, but
- the automation's "What it has done" log gains **no entry at all**;
- the sequence's "Who is going through this" still says **Nobody yet**.
Pressing **Try it out** on the same automation immediately logs
`RAN FINE · PRACTICE RUN · Sequence: would start them on it` — so the evaluator, the
condition logic and the step executor all work. **What is missing is the live event
dispatch:** nothing publishes domain events (tag added/removed, offer purchased, form
submitted, lesson/course completed, event registered/attended, quiz finished, payment
failed, subscription cancelled, contact created, abandoned checkout, anniversary) into the
automation runner.
**Why this is the top priority:** every "it's already built" marketing feature — form tags,
quiz result sequences, post-purchase onboarding, dunning follow-up, event reminders —
depends on this. Until it exists, the 17 triggers and 11 actions in the UI do nothing.
**Build:** a single event bus. Every mutation that corresponds to a trigger emits a typed
event; a worker matches enabled automations, evaluates conditions, executes steps in order
(honouring `wait`), and writes a run record with per-step outcome. Add idempotency (don't
re-run the same automation for the same event), a retry policy, and an integration test per
trigger that asserts both the run log entry and the side effect.

### P0-0b. The quiz editor discards every text field
**Reproduce:** open a quiz, add a question, type the question text, an answer label and its
point value using the keyboard, press Tab, then reload the page.
**Observed:** the question and answer **rows** persist, and the two `<select>`-backed fields
(result tag, result sequence) persist — but **every text value is gone**: question text,
both answer labels, both point values, the result name, the result button label, the button
URL and the result body all revert to `New question` / `New answer` / `0` / `New result` /
empty. The page states "Changes here save themselves as soon as you move on to the next
box." Verified with real typing plus Tab plus a full reload, not just scripted input.
**Consequence, confirmed on the public page:** the live quiz renders
`New question` with two `New answer` options, and a completed attempt is logged as
**"0 out of 0"**. The quiz flow itself is fine (start → question → email gate → result), so
this one bug is the only thing making quizzes unusable.
**Fix:** persist text inputs on debounce/blur like the selects already do, and surface a
save state. Then re-test that points sum into a real score and select the right result band.

### P0-1. Public form pages never collect a name or an email address — forms capture nothing usable
**Reproduce:** create a form at `/admin/marketing/forms-v2`, add one short-answer question,
save, open `/f/<slug>`, submit.
**Observed:** the public page renders only the custom question and a Submit button. There
is no name field and no email field. The submission is stored as a reply with
`"No name given"` and no email. No contact is created, no tag is applied, no email sequence
starts — so the form's own "Tags added when somebody replies" and "Emails they start
getting" settings can never fire.
**Fix:** always render name + email on a public form (as the offer order form already
does — "Their name and email are always asked for"), require email, and on submit:
upsert the contact, apply the configured tags, enrol them in the configured sequence, create
the enquiry, and fire the `form_submitted` automation trigger. Backfill/repair existing
anonymous replies where possible.

### P0-2. Subscriber counts disagree across five screens
**Observed on the same data set (5 contacts, all flagged "Happy to hear from you"):**
- `/admin/contacts` → 5 people, all subscribed
- `/admin/segments` "everyone" group → 5 people
- `/admin/subscribers` → **0 subscribers**
- `/admin/analytics` "On your email list" → **0**
- `/admin/` dashboard "People who joined your list" → **3**
- Email campaign composer, audience "Everyone on my email list" → **"0 people will get this"**
**Fix:** define one canonical "email list membership" predicate (subscribed AND not
bounced AND not unsubscribed) in a single query/helper, and make Subscribers, Analytics,
Dashboard, Segments, and the campaign audience estimator all use it. The campaign
estimator computing 0 means broadcasts currently send to nobody — treat this as a
send-blocking bug.

### P0-3. Form question editor silently loses work
**Reproduce:** open a form, "Add the first question", fill it, press "Add it", navigate away.
**Observed:** the question appears in the list but is discarded — the parent form still needs
a separate "Save form" press, with no dirty-state indicator and no unsaved-changes warning.
**Fix:** either persist the question immediately on "Add it", or add a visible unsaved
badge + `beforeunload`/route-change guard. Apply the same audit to every nested editor
(offer tabs, quiz questions/results, event dialog, sequence emails, community badges).

### P0-4. New events are created without a timezone, so their time renders wrong
**Reproduce:** create an event at `/admin/marketing/events-v2`. The create dialog says
"Eastern time — you can change this next" but offers no timezone field. Enter
`2026-09-15 18:00`.
**Observed:** the list renders `Sep 15, 2026, 3:00 PM` — a 3-hour shift. Opening the event's
edit dialog shows the stored value is correct (`2026-09-15T18:00`) and reveals a timezone
selector defaulted to `America/New_York`. **Pressing Save event once** makes the list render
correctly as `Sep 15, 2026, 6:00 PM EDT`, and the public event page then reads
"Tuesday, September 15 at 6:00 PM EDT".
**Diagnosis:** creation does not persist a timezone, so the renderer falls back to
something else until the event is opened and re-saved.
**Fix:** capture the timezone in the create dialog (default to the site timezone) and
persist it with the event; render through it everywhere. Add tests across DST boundaries.
Backfill existing events created without one.

### P0-5. Saving a new offer fails silently when no price is set
**Reproduce:** `/admin/offers/new`, fill name + description + entitlement, press Save.
**Observed:** nothing happens, no error, the URL stays on `/new`. It only saves once a
price is entered on the Price tab.
**Fix:** show inline validation naming the missing field and switch to the offending tab.
Audit every "Save" in the admin for silent failure.

### P0-6. A dry run reports success for a step that cannot do anything
**Correction to an earlier read of this app — the validation here is mostly good.** With an
unconfigured step the app *does* badge the automation **NEEDS ATTENTION**, explains
"This is running, but it cannot do everything it says. Its runs will report the problem",
names the exact fault ("step 1 (add a tag) has no tag chosen"), badges the step
**UNFINISHED**, and clears all of that once the step is configured. Removing a step also
raises a proper "Remove this step?" confirmation, and adding one opens a config dialog.
**The one real defect:** pressing **Try it out** on such an automation logs
`RAN FINE · PRACTICE RUN · Tag: none chosen` — success, for a step that would have done
nothing.
**Fix:** the run log should record that step as skipped/warning, and the overall verdict
should be "ran with problems", not "ran fine". Also consider refusing to activate an
automation that is in the needs-attention state at all.

### P0-7. "Send me a test email" gives no feedback
`/admin/settings/email` → "Send me a test email" produces no toast, no success state and no
error, so there is no way to tell whether SMTP works.
**Fix:** return and surface the result (sent / provider error / not configured), and add
the same feedback to every fire-and-forget action.

### P0-8. `/admin/community/:id` errors for some ids
`/admin/community/1` renders "We couldn't load this community. Try refreshing the page."
while `/admin/community/2` works.
**Fix:** correct the id/route resolution and render a proper 404 for a genuinely missing
community rather than a generic failure.

### P0-9. Plans cannot be edited and grant nothing
A plan created at `/admin/sales/plans` offers only **Delete plan** — no edit — and there is
no field for what the plan gives access to, so a subscription to it unlocks nothing.
**Fix:** add plan editing, and add entitlements (courses / communities / downloads /
coaching) to plans, the way offers already have "What do they get?".

### P0-10. Section/lesson editing gaps in the course builder
Sections cannot be renamed or reordered independently (the chevron only collapses), and
there is no per-section or per-lesson drip schedule even though
`/admin/settings/delivery` exposes a global "Drip release time" that nothing consumes.
**Fix:** see P1-1.

### P0-11. Smaller defects found while testing
- **Podcast episodes save as LIVE with no audio.** Adding an episode with only a title
  produces a row reading `ZZ Test — episode one · No audio yet · LIVE`, i.e. a listener-facing
  episode with nothing to play. Require audio before an episode can go live, or default new
  episodes to draft.
- **Tag chips on the contact record need a very precise click.** The first click on
  `+ Retreat Waitlist 2027` at `/admin/contacts/:id` did nothing; a second, better-centred
  click applied it. Enlarge the hit area and give the chip a pressed/loading state.
- **A public form/event submission that fails gives no error.** One of two otherwise
  identical event registrations produced no contact and no confirmation, with nothing shown
  to the visitor. Every public submit needs an explicit success and failure state.
- **Coaching sessions can only be booked for members**, not for any contact — the client
  picker lists only people with an account (2 of 6 contacts), so someone who bought coaching
  without creating a password cannot be booked in.
- **Confirmation dialogs are invisible to assistive tech / text extraction.** "Stop selling"
  and "Remove this step" both open a confirm prompt whose buttons ("Yes, stop selling it" /
  "Never mind", "Remove it" / "Never mind") do not surface in the accessibility tree as part
  of a labelled dialog, which makes the action look broken until you find them. Give every
  confirm a proper `role="dialog"` with an accessible name, focus trapping and initial focus.
  (The underlying actions themselves work correctly once confirmed.)

## PHASE 1 — MISSING FEATURES VS KAJABI

Ordered by business impact. Each item states what Kajabi does, what exists here today, and
what to build.

### P1-1. Course product depth: drip, paywall, certificates, live rooms  ⭐ biggest product gap
**Kajabi** (observed at `/admin/products/:id`, `/edit`, `/certificate_template/edit`) — a
course product has tabs **Outline / Customize / Offers / Customers / Certificates /
Settings / More**, and the Outline is a drag-and-drop tree of modules and posts each with
its own Draft/Published state. Specifically:
- **Per-module (category) drip**, with the release hour set globally in
  Settings → "Drip settings — Choose what time of day Drip modules will become available".
- **A Paywall element you drag into the outline.** Adding it auto-creates a **"limited access
  product"** twin of the course — a second product members can hold that shows only the
  content *above* the paywall, with a chosen **paywall offer** presented when they hit gated
  content. The live account has both `test` and `test - limited access` offers.
- **Certificates tab** with a real designer: logo, certificate title, recipient subtitle,
  show student's name, course subtitle, include course title / completion date /
  **unique certificate serial number** / **expiration date** / a custom field, and a
  background image. Emailed automatically on course completion.
- **Live Rooms** — "provide a live video session for this course", up to 200 participants.
- **Community linking** — attach an existing community circle to the course member experience.
- **Comment settings** — enable comments per course, override per lesson, and "lock all
  comments" (existing comments stay visible, no new ones).
- **Customers tab** per product.
- **Course generator** — AI-generated course outline ("Your course outline was created
  successfully!"), plus an embedded "Cofounder" AI assistant across the admin.

**Today:** curriculum is sections → lessons only, with no section rename/reorder/settings, no
paywall, no drip consumption (the global release hour in `settings/delivery` is wired to
nothing), no certificate generator behind the existing "Certificate issued" email, no live
rooms, no course↔community link, no comments, and no per-product customers view.

**Build:**
- Section edit dialog: rename, reorder, "release X days after purchase" / "release on
  date" / "release immediately", visible/hidden.
- Lesson-level release override, plus `prerequisite: previous lesson must be complete`.
- Consume `settings/delivery` release hour + timezone when computing unlock times.
- Member-facing locked state with the unlock date, and a nightly job that fires the
  `lesson_unlocked` notification.
- Completion: mark-complete per lesson, % progress per course (already reported in
  "How far people get"), course-complete event, and a real PDF certificate delivered by the
  existing "Certificate issued" email — with the full Kajabi field set above, including a
  unique serial number and optional expiration date, plus a certificate designer screen.
- Drag-and-drop reordering of sections and lessons; per-section and per-lesson
  Draft/Published.
- **Paywall element** in the outline + the auto-generated limited-access twin product and its
  paywall offer.
- **Live room** per course (a scheduled video session members join from inside the course).
- **Course ↔ community link**, so buying the course joins them to a channel.
- A per-course **Customers** tab (who is enrolled, progress, last activity).
- Optional: an AI "generate a course outline from a topic" action, matching Kajabi's Course
  generator.

### P1-2. Lesson content types
**Kajabi** (observed at `/admin/posts/:id/edit`): title, module selector, **Media: None /
Video / Audio**, **Downloads (Add Files)** — multiple attachments, a rich body editor,
**per-lesson Automations**, Draft/Published, lesson thumbnail, and
**Comments: Visible / Hidden / Locked** with a comment-settings link.
**Today:** name + one video (upload or pasted link) + rich-text notes + duration + "free
taster" + visible. No attachments, no audio, no thumbnail, no automations, no comments.
**Build:** multiple attachments/downloads per lesson, an audio lesson type, a lesson
thumbnail, per-lesson automations (reusing the global registry), an embedded
assessment/quiz block (P1-7), and per-lesson comments with Visible/Hidden/Locked (P1-3).

### P1-3. Comments and a unified inbox
**Kajabi:** comments on course posts with moderation, plus a **Universal Inbox** at
`/admin/sites/:id/universal_inbox` that unifies every conversation.
**Today:** community posts have counters for comments/reactions but no admin reply UI.
`/admin/conversations` holds only AI website chats; `/admin/leads` holds only enquiries.
**Build:**
- Lesson comments: post, reply as host, pin, hide, delete, per-course on/off; notify on new
  comment; `comment_posted` automation trigger.
- Community: admin reply/react on posts, moderation queue, member mute/remove.
- One inbox at `/admin/inbox` merging enquiries + AI conversations + lesson comments +
  community mentions, with unread/assigned/resolved states.

### P1-4. Email builder — blocks, images, buttons, templates
**Kajabi:** a visual block editor (text, image, button, divider, video thumbnail, product
card, columns), saved templates, and a "Email templates" library.
**Today:** campaigns get a 6-button inline toolbar (bold/italic/H2/list/link) + "See how
it looks"; **sequence emails are a plain textarea with no formatting at all**; newsletters
get the same small toolbar as campaigns.
**Build:** one shared block-based email composer used by campaigns, sequences,
newsletters, and the system-email editor. Blocks: heading, paragraph, image (from Media
Library), button/CTA with link, divider, spacer, two-column, product/offer card, social
row. Saveable/duplicatable templates. A live desktop + mobile preview. Full merge-tag
palette with a picker (`firstName`, `lastName`, `email`, `offerName`, `courseName`,
`unsubscribeUrl`, `loginUrl`, custom contact fields) — today only `{{firstName}}` is
documented.

### P1-5. Campaign audience, scheduling and event-relative sends  ⭐ (verified in Kajabi)
**Kajabi** (observed at `/admin/sites/:id/email_campaigns`) puts broadcasts *and* sequences
in **one list** with **Folders**, **Manage Templates**, a Type column (Broadcast / Email
Sequence) and statuses **Active / Draft / Scheduled**. Critically, campaigns can be scheduled
**relative to an event**, not just to a clock:
- `24 hours before 'The Do's & Don'ts CEU' event on September 25, 2026 10:00 PM` — Scheduled
- `2 hours before …` — Scheduled
- `7 days before …` — Scheduled
- `9 hours after …` — Scheduled
- `Upon 'The Do's & Don'ts Educational' event registration` — Active
Kajabi also offers **granular email preferences** — "let contacts choose which emails they
receive instead of unsubscribing from everything" (topic-level subscription).

**Today:** four hard-coded audiences (`Everyone on my email list`, `Everyone with a
membership`, `Everyone who's enquired`, `Everyone in my community`), immediate **Send** only,
no test send, no schedule, no folders, no templates, no event-relative timing, and
unsubscribe is all-or-nothing.

**Build:**
- Audience = any combination of groups/segments, tags and product/offer ownership, plus
  exclusions, with a live recipient count (fix P0-2 first).
- "Schedule for later" with a timezone, plus cancel-scheduled-send.
- **Event-relative scheduling**: N minutes/hours/days before or after an event's start, and
  "upon registration" — reusing the Events module (P1-14 events section).
- "Send a test to me" and subject-line A/B with an automatic winner.
- Folders and a saved-template library shared with sequences and newsletters.
- **Topic-level email preferences**: define subscription topics, let contacts manage them on
  a preference-centre page, and honour them at send time.

### P1-6. Coaching programs and native scheduling  ⭐ (verified in Kajabi — much deeper than a booking link)
**Kajabi** (observed at `/admin/coaching_programs/:id` and
`/admin/sites/:id/scheduling/settings/edit`):
- A **coaching program** is a product with tabs **Clients / Package outline / Offers / Settings**.
- **Package outline** = a numbered session plan (the live example has **24 sessions**), each
  with its own actions, plus an "Additional session default" template.
- **Clients** tab: Active / Past, with per-client info and progress.
- **Settings → Scheduling preference**: either **Kajabi-native** ("Set availability and book
  sessions inside of Kajabi") **or** an external link (Calendly / Acuity / Google Calendar).
- **Location per session**, including **Kajabi Live Video** — a built-in 1-hour video room.
- **Per-session reminders**: "Send a reminder [N] before the session start time", multiple
  reminders addable/removable.
- **Session duration** and **Manage default availability**.
- **Kajabi Live Recording**: automatically upload the session recording into the session record.
- **Additional purchases**: "Offer additional 1:1 coaching sessions" — clients buy more
  sessions inside the program.
- **Notifications matrix**: coach vs client, per event ("when a change to the coaching
  session is saved (shared notes, resources…)", "when a recording is uploaded").
- Site-level **Scheduling** page: weekly availability grid (Sun–Sat) with "You don't have
  availability on Mondays" states, **slot frequency**, **open date range** ("clients can book
  up to 6 months ahead"), **session limits per day**, and **calendar connections** —
  Google Calendar (live-connected in the account, with "Add to calendar" + "Check for
  conflicts" across multiple named calendars), Microsoft Office 365, Microsoft Outlook,
  iCloud Calendar, Calendly.

**Today:** a coaching offer is name + description + session count + minutes + price +
**a pasted Calendly URL** + live toggle. `settings/coaching` has booking/cancellation
windows, slot granularity and open-window days. **Session records DO exist and work** —
"Book a session" on the Sessions tab captures client, parent offer, date/time, status,
meeting link, a client-visible agenda and private notes. What is missing is everything
around them: no availability grid, no calendar connection, no member-facing booking (the
admin books manually), no program/session outline, no reminders wired to real sessions, no
recordings, no extra-session purchases, and the client picker only lists people who already
have an account.

**Build, in this order:**
1. **Coaching program** entity: session outline (numbered sessions, reorderable, with a
   default template for extra sessions), per-session title/agenda/shared resources/private
   notes/status/recording.
2. **Clients tab**: enrolled clients, progress through the outline, active vs past.
3. **Availability**: weekly grid + date overrides + blackout dates, slot frequency, per-day
   session caps, booking-window days (reuse the existing `settings/coaching` values).
4. **Calendar sync**: Google Calendar first (two-way: write the booked session, read
   multiple calendars for conflicts), then Microsoft/Outlook. Keep "paste an external link"
   as an explicit alternative mode, not the only mode.
5. **Native booking page** for members that respects availability, windows and caps.
6. **Reminders**: multiple configurable offsets per program, wired to the existing
   "Coaching reminder" system email; plus a coach/client notification matrix.
7. **Video**: a meeting link per session (Zoom/Meet/Whereby), and recording attachment to
   the session record.
8. **Additional session purchases** inside a program.
9. Group coaching (many attendees per session).

### P1-7. Assessments (graded, in-course) as distinct from quizzes

### P1-8. Funnel blueprints and email steps
**Kajabi:** a library of prebuilt funnel blueprints (freebie/opt-in, sales, webinar,

**Today:** funnels are manual stage lists (landing / sign-up / your offer / extra offer /

**Build:** blueprint templates that scaffold stages, forms, tags and a sequence in one

### P1-9. Offers, checkout and pricing depth  ⭐ (verified in Kajabi — the largest single gap)
Observed in Kajabi at `/admin/offers/:id/edit`, `/details/edit`, `/upsells`,
`/settings/edit`, `/admin/sites/:id/coupons` and `/admin/sites/:id/edit/checkout-settings`.
Your offer editor is well structured but models **one price and one product**; Kajabi models
a catalogue-grade offer.

**9a. Multiple pricing options per offer** — a single Kajabi offer carries several price
points side by side, e.g. *Lounge VIP* = `$3,497.00 one-time payment` **and**
`$347.00/month for 6 payments`, each with its own taxes-included flag and a quantity limit
("Unlimited"). The offers index shows "Multiple pricing options" for 7 of 44 offers, and the
checkout renders them as selectable payment options.
*Today:* one price per offer, so the shop needs two separate offers for PIF vs plan.
**Build:** a `pricing_options[]` collection on an offer (type, amount, interval, count,
tax-included, quantity cap, label, default), rendered as a chooser at checkout.

**9b. Multiple products per offer + access limits** — Kajabi's Details tab has
"Products in this Offer" (the example bundles two), an **internal title** separate from the
customer-facing title, and **Product Access**: "Begin access at a specific date" and
"Restrict access to a specific amount of days".
*Today:* multiple entitlements ✓, access-expiry presets ✓ (30/60/90 days…), but no
scheduled start date and no internal title.
**Build:** internal title; "begin access on date"; free-form access duration in days.

**9c. Upsell **and downsell** funnel** — "The first upsell page is shown immediately after
purchase and can be followed by additional upsell or downsell pages", drawn from a reusable
**Upsells** library (there is an `Upsells` tab on the offers index, i.e. upsells are
site-level objects reused across offers, not per-offer only).
*Today:* per-offer upsells, no downsell branch, no shared library.

## PHASE 2 — UI AND THEME REWORK

The owner's feedback: *the light purple looks cheap; make it black, richer, more
beautiful.* The public site (`bossclinician.callsphere.site`) already nails this — near-black
ground with a warm gold accent and a serif display face. **The admin should inherit the
public site's identity instead of inventing a purple one.**

### What to remove
- The lavender/violet surfaces (`#2A2140`-family) on cards, dialogs, table headers, tab
  bars and inputs.
- The purple-tinted page background and the purple glow behind dialogs.
- Purple as a semantic colour — it currently reads as both "brand" and "selected", so
  neither is legible.

### Target palette (dark-first, replace the purple ramp with a neutral one)
```
--bg-base        #08070A   page ground, near-black, very slightly warm
--bg-surface     #101014   cards, panels
--bg-surface-2   #16161B   nested panels, table header, dialog body
--bg-elevated    #1D1D23   dialogs, popovers, hover
--border-subtle  #23232B   hairlines between rows
--border-strong  #33333D   input borders, card edges
--text-primary   #F2EFE9   warm off-white, never pure #FFF
--text-secondary #A8A49C
--text-muted     #6F6B64
--accent         #D4AF6E   the gold already used on the public site
--accent-hover   #E4C486
--accent-ink     #0B0A08   text on gold buttons
--success        #6FBF8B
--warning        #E0A94B
--danger         #E06C6C
--info           #7FA8D9
```
Rules:
- Exactly **one** accent (gold). Use it for the primary button, the active nav item, the
  active tab underline, focus rings and links — nothing else.
- Status colours never double as brand colours. Badges use a 12% tint of the status colour
  with the status colour as text, not a solid fill.
- Elevation comes from **surface lightness + a 1px hairline**, not from coloured glows.
  Dialogs: `background: --bg-elevated`, `border: 1px solid --border-strong`,
  `box-shadow: 0 24px 60px rgba(0,0,0,.55)`, and a plain `rgba(0,0,0,.6)` scrim — remove the
  purple bloom.

### Typography
- Keep the serif display face (the public site's) for page titles and dialog titles only.
- Body, tables, labels and buttons: one clean sans (Inter / Söhne / system stack), 14px
  base, 15px for prose.
- Section eyebrows ("SALES", "MARKETING"): 11px, letter-spacing .12em, `--text-muted` —
  keep this, it is one of the nicer touches already there.
- Numbers in tables and metric cards: tabular figures (`font-variant-numeric: tabular-nums`).

### Layout and density
- Sidebar `#0B0A0D`, one shade darker than the page, hairline right border, active item =
  gold left rule 2px + `--bg-surface` fill + `--text-primary` label. Drop the purple pill.
- **Fix the horizontal overflow.** Several admin pages (dashboard metric strip, offers
  table, contacts table) currently scroll the whole page sideways and clip content at the
  right edge. Constrain the content column to `max-width: 1440px` and give wide tables their
  own `overflow-x: auto` container.
- Metric cards: 1px hairline, no gradient, label 11px muted uppercase, value 28px, delta as
  a small tinted badge. Remove the coloured underline bars.
- Tables: 44px rows, sticky header on `--bg-surface-2`, `--border-subtle` row dividers,
  hover `--bg-elevated`, right-aligned numerics, and row actions revealed on hover.
- Real empty states: icon in a 40px rounded square at 8% accent tint, one-line headline, one
  line of help, one primary action.

### Interaction polish (all currently missing or inconsistent)
- **Make the existing toast system universal.** Toasts already exist and look right (adding
  an order bump shows "Order bump added."), but most saves signal only via a small "Saved"
  text swap and several actions — "Send me a test email", failed public form submits, some
  publish toggles — signal nothing at all. Every mutation should emit success or error, with
  undo where it applies.
- Inline field-level validation with the message under the field, and tab-switching to the
  first invalid field.
- Dirty-state badge + navigation guard on every editor (also P0-3).
- Skeleton loaders instead of blank panels.
- Visible `:focus-visible` gold ring on every interactive element, full keyboard operation
  of tabs and dialogs, `aria-live` on toasts.
- Destructive confirmations that name the object being deleted.
- Respect `prefers-reduced-motion`; keep transitions ≤150ms.

### Deliverable for this phase
Centralise the above as CSS custom properties in one theme file, delete hard-coded purple
hex values throughout the admin, and add a short `THEME.md` documenting the tokens and the
one-accent rule so the next feature does not reintroduce a second brand colour.

## HOW TO WORK

1. Land Phase 0 as separate, individually reviewable PRs with a regression test each.
2. For Phase 1, work top-down; P1-1, P1-4, P1-5 and P1-6 unlock the most value.
3. Every new module must reuse the existing patterns already in the codebase: the segment
   rule builder, the automation trigger/condition/action registry, the tag picker, the
   offer entitlement selector, and the report shell.
4. Add each new event to the automation trigger list and each new action to the automation
   step list, so new features are usable from the existing engine.
5. Do not touch the public marketing site's design, the page builder, or anything mobile-app
   related.
